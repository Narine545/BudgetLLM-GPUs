# Как дополнить базу

Спасибо, что заглянули. Самое ценное здесь — **замеры из реальных сборок**: половина таблиц собрана по единичным отчётам,
и цифра с одной карты меняет всю картину по модели.

## Что приветствуется

| Тип вклада | Что нужно приложить |
| --- | --- |
| **Замер скорости** | модель и квантизация, длина контекста, бэкенд (llama.cpp / Ollama / vLLM / ExLlama), железо, команда или настройки, результат. Ссылка на отчёт или лог — идеально |
| **Опыт модификации** | что делали, чем (ссылка на инструмент), что получилось, что пошло не так, как карта выглядит в системе |
| **Сборка** | состав, платформа, что сработало и что нет, порядок цен |
| **Исправление** | конкретная строка в `assets/data/*.js` + источник, который её подтверждает |
| **Новый источник** | ссылка + фраза, что именно из неё следует |
| **Русскоязычные материалы** | база писалась под RU-аудиторию; отчёты с overclockers.ru, habr, serverflow особенно ценны |

## Процесс

```bash
git clone https://github.com/Narine545/BudgetLLM-GPUs.git
cd BudgetLLM-GPUs
git checkout -b data/my-card-benchmark

# правите assets/data/*.js — схема в docs/SCHEMA.md
node tools/validate.js          # обязательная проверка данных
npm i && npm run smoke          # интерфейс: разделы, фильтры, сравнение, подбор
```

Дальше — pull request. В описании хватит трёх пунктов: **что добавили**, **откуда данные**, **чем проверили**.

## Требования к данным (проверяются автоматически)

1. Каждому замеру — `src` из реестра `meta.sources` и уровень достоверности:
   - `measured` — владелец приложил результат на своём железе;
   - `reported` — сообщение в трекере/на форуме без лога;
   - `estimated` — посчитано по формуле, `src: null`;
   - `vendor` — данные производителя.
2. Никаких цифр без контекста: модель, квантизация, контекст, бэкенд.
3. Модификация указывает на существующий инструмент в `tools.js` и явно говорит, **нужен ли паяльник**.
4. У цены есть дата и оценка волатильности; для карт с известной историей — точка в `prices.history`.
5. Сток и мод описываются раздельно, включая то, что модификация **не** даёт. Отдельно ценятся строки «что не сработало».

## Чего не принимаем

- Рекламные материалы и партнёрские ссылки на магазины; сравнения «в пользу» продавца.
- Цифры без источника или «по слухам».
- Инструкции по обходу лицензий и платежей; дампы VBIOS и бинарники прошивок (см. [SECURITY.md](SECURITY.md)).
- Рекомендации карт, у которых нет ни замера, ни известного сценария использования.

## Стиль текста

- Пишем по-русски, спокойно и по делу; термины — как принято в сообществе (`prefill`, `tok/s`, `MoE`, `квантизация`).
- Ограничения важнее достоинств: у каждой карты в базе должно быть видно, где она ломается.
- Числа — с единицами и без округлений «на глаз»: `38 tok/s при 4096`, а не «около 40».
- Никаких неоновых «геймерских» эпитетов: тон — инженерный отчёт, а не обзор с витрины.

## Что делать, если не сходится

Если `validate.js` ругается на ваши данные — сообщение почти всегда говорит прямым текстом, какого поля нет
или куда ведёт несуществующая ссылка. Если непонятно, открывайте issue: разберёмся вместе.
